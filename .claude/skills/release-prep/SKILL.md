# リリースの準備

作業が終わったら、次の順に進める。**本人の最終承認を受けるまで公開しない。**

1. **状態の確認**: 変更をコミットし、前回のタグ（`git describe --tags --abbrev=0`）を確認する。
2. **コードレビュー**: `/code-review high` で前回のタグ以降の全差分を見る。指摘は未検証の候補として扱い、コードや実測で確かめてから直す。見送る指摘は理由を残す。修正したらテストを通常時と `CLAUDEBAR_FORCE_LEGACY=1` の両方で通し、修正の差分に新しい問題がないようレビューを繰り返す。
3. **リリースノートの下書き**: `docs/release-notes/v<バージョン>.md` を、前回のタグ以降の全コミット（`git log <タグ>..HEAD`）から書く。利用者に見える変更を先に書き、未確認のことを確認済みのように書かない。
4. **README の最新化**: `README.md` と `README.en.md` を今回の変更に合わせて同時に更新する（機能、動作環境、権限、ビルド手順）。
5. **CI**: 許可があれば push し、`gh run` で成功を確認する。
6. **チェック**: `docs/RELEASE_CHECKLIST.md` の手動項目を実機で確かめ、`main` へマージしてから `./scripts/preflight.sh <バージョン> --confirmed` を実行する。
7. **止まって報告**: レビューの結果、リリースノート、確かめた項目、確認できなかった項目を報告し、「公開して」の返事を待つ。
8. **公開**: 本人が今の報告に対して公開を明示したら、`./scripts/release.sh <バージョン> --approved=v<バージョン>` を実行し、Release、appcast、Homebrew の状態を確かめて報告する。

## してはいけないこと

- 7 の報告より前の発言や、別のバージョンへの承認を、最終承認として扱うこと
- 報告のあとにコミットを足して、そのまま公開すること（6 からやり直して、もう一度承認を受ける）
- 本人の承認なしに `--approved` を付けること。タグの作成や `main` への push で公開を先行させること
