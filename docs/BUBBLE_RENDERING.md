## 1. レイヤーモデル

単体バブル（`BubbleView`）と3つ表示（`BubbleSphere`）は**同じ積み方**をする。
3つ表示は「単体バブルを 72pt / 62pt / 50pt の3サイズで描いたもの」であること。

```
        ┌───────────────────────────────────────────────┐
   前面 │ ⑦ グロス芯    （細く鋭い光の弧・plusLighter）  │  ← 光源そのもの
        │ ⑥ グロス暈    （太く柔らかい弧・screen）      │  ← 空の映り込み
        │ ⑤ 裏面反射    （右下の小さな点・screen）      │  ← 凹面鏡の像
        │ ④ フレネル縁  （最外周だけ急に光る・screen）  │  ← 縁の輝き
        │ ③ 薄膜帯（虹）（縦の虹を縁へ寄せる・screen）  │  ← 干渉色
        ├───────────────────────────────────────────────┤
        │ ② 中身        リング → ロゴ/％/キャプション   │  ← 情報
        ├───────────────────────────────────────────────┤
        │ ① 拡散照明    （左上から広く淡く・screen）    │  ← 全体の膨らみ
        ├───────────────────────────────────────────────┤
   背面 │ ⓪ ガラス玉    Liquid Glass `.regular`         │  ← 素通し＋ぼかし
        └───────────────────────────────────────────────┘
                        （この下は透明ウィンドウ＝デスクトップ）
```

③〜⑦ は `BubbleGlossOverlay`、① は `BubbleDepthUnderlay`（ともに
`Sources/ClaudeBar/Components/BubbleDecoration.swift`）。**単体と3つ表示で完全に同じ部品**。

| # | レイヤー名 | 実体 | 形 | 合成 | 実装 |
| --- | --- | --- | --- | --- | --- |
| ⓪ | ガラス玉 | Liquid Glass `.regular` | Circle | 素材 | 単体 `PanelViews.swift:152` `SingleBubbleGlass` / 3つ `TripleBubbleView.swift:106` `TripleBubbleGlass` |
| ① | 拡散照明 | RadialGradient 白 | Circle | `.screen` | `BubbleDecoration.swift:71-91` |
| ② | 中身 | リング＋テキスト | — | 通常 | 単体 `PanelViews.swift:675-724` / 3つ `TripleBubbleView.swift:168-212` |
| ③ | 薄膜帯（虹） | 縦LinearGradient × 径方向マスク | Circle | `.screen` | `BubbleDecoration.swift:101-108` |
| ④ | フレネル縁 | 径方向ランプ × 方位マスク | Circle | `.screen` | `BubbleDecoration.swift:112-124` |
| ⑤ | 裏面反射 | 小さなRadialGradient | 8·s pt の点 | `.screen` | `BubbleDecoration.swift:159-167` |
| ⑥ | グロス暈 | 円弧ストローク（太・ぼけ） | trim 0.51–0.77 | `.screen` | `BubbleDecoration.swift:130-142` |

> ③薄膜 → ④フレネル → ⑥暈 → ⑦芯 → ⑤裏面反射 の順に書かれている。
> 加算合成なので順序は見た目にほぼ影響しない（`.screen` は可換に近い）。

### スケール `s`

すべての寸法は **基準径 72pt を 1 とするスケール `s`** で駆動する。

- 単体: `s = PanelController.bubbleScaleFactor(使用率)`（`PanelController.swift:110`、
  10%ごとに+1%、100%で1.1倍）
- 3つ表示: `s = diameter / 72`（`TripleBubbleView.swift:128` / `:154`）
  - セッション 72pt（使用率で膨らむ）/ Fable 62pt / 週間 50pt
    （`TripleBubbleCluster.swift:30-37`）

**新しい定数を足すときは必ず `* s` を付ける。** 付け忘れると 50pt の球だけ縁が太い、
ぼかしが効きすぎる、といった「小さい球だけ別物」現象が起きる。
（唯一の例外は**文字サイズ**。50pt球で9ptまで落ちると読めないので比例させない。
単体バブルも膨らむとき文字だけ固定サイズを保つのと同じ考え方）

## 3. 物理の語彙

依頼の精度を上げるための共通言語。ここで使う言葉はコード中のコメントとも揃えてある。

- **フレネル反射 (Fresnel)** — 界面の反射率は視線と面の角度で変わる。
  `F = F₀ + (1−F₀)(1−cosθ)⁵`、水／シャボン膜の `F₀ = 0.02`。
  正射影の球では `cosθ = √(1−u²)`（`u = r/R`）なので、**最外周 1pt 前後だけが急激に明るい細いランプ**になる。
  → 「幅が一定の白い縁取り」は偽ガラスの最も典型的な失敗。フレネルは必ず**外周に集中**させる。

- **2ローブのスペキュラ (two-lobe specular)** — ハイライトは形の違う2つで作る。
  **芯** = 光源そのものの像（小さく鋭い）、**暈（ローブ）** = 空全体の映り込み（大きく淡い）。
  同じ弧を太さ違いで2本引いても球には見えない。芯は暈より**短く・内側・鋭く**。

- **裏面反射 (back-surface reflection)** — 球の内側（凹面鏡）に映る反転した光源像。
  前面ハイライトの**対角**に、暗く小さく出る。これがあると「膜が2枚ある立体」に見える。

- **薄膜干渉 / 重力縞 (thin-film interference / gravity banding)** —
  シャボン膜の色は膜厚で決まる。膜は重力で下へ流れて厚くなるため、
  **色は縦方向に変化する**（`filmStops` は膜厚 250→560nm を上→下に並べたもの）。
  角度方向に均一な虹リングは物理的に誤り。さらに干渉は反射成分なので、
  フレネルと同じく**縁に寄せる**（実物のシャボン玉の縁だけが虹色に見える理由）。

- **コースティクスの光だまり (caustic light pool)** — レンズが光を集めて床に作る明るい溜まり。
  ガラス球なら足元に出るが、**シャボン玉には出ない**（下記）。現在の実装には無い。

- **色収差 (chromatic aberration)** — 屈折率が波長で違うため、強い屈折の縁で
  RGB がわずかにずれる。現在はグロスに入れていないが、「縁の光にほんのり色を」という
  依頼はここに当たる（`GlassTubeRim` が過去にやっていた手法）。

### やってはいけない物理

1. **背景を屈折（歪ませ）ない。**
   シャボン玉は厚さ数百nmの薄膜で、入射光と射出光が平行になる。だから
   **背景は歪まない**。ガラス球のような集光・全反射・光だまりを入れると
   「シャボン玉」ではなく「クリスタルボール」になる。

2. **そもそも macOS では屈折できない（実測）。**
   Liquid Glass の屈折（レンズ）は**自ウィンドウ内のコンテンツにしか掛からない**。
   透明ボーダレスウィンドウの背後（デスクトップ）は、ぼかしと色の採取はされるが
   屈折はされない。`NSGlassEffectView` でも同じ（詳細はメモリ `liquid-glass-limits`）。
   つまり「背景を歪ませて」という依頼は、物理的にも API 的にも実現できない。

3. **光は塗料ではない。**
   `.fill(.white.opacity(x))` の不透明な膜は背景の模様を**置き換えて**しまい、
   一瞬でシール感が出る。`.screen` / `.plusLighter` なら背景の質感が透けたまま明るくなる。

## 4. 変えてはいけない制約

| # | 制約 | 理由 |
| --- | --- | --- |
| 1 | **常時アニメーションは CAAnimation だけ**（`WobbleHost` / `DriftHost` / `startFloating`） | SwiftUI の `TimelineView` / `.repeatForever` はアプリ内で毎フレーム刻む。実測で待機中 **7–13% CPU**。24時間常駐のメニューバー要素として許容できない（現在 約1%） |
| 2 | **`glassEffect` に `.opacity()` を掛けない** | 屈折像と素の背景の線形クロスフェードになるだけで、ガラスが「薄く」ならず質感が消える |
| 3 | **黒い暗幕・黒いブラー・影を入れない** | 暗幕・ティント・ターミネーター・影はいずれも「黒いブラー」として悪目立ちする（オーナー確認済みで全廃）。球体表現は**白い光だけ**で作る |
| 4 | **光は加算合成**（`.screen` / `.plusLighter`） | #3 の裏返し。不透明な白で塗ると背景の模様が消えてシールになる |
| 5 | **光源は左上ひとつ**。全レイヤーがこれに従う | グロスの弧（trim 0.51–0.77 = 左上）、拡散照明の中心 (0.33, 0.28)、フレネルの方位マスク（上が最も明るい）、裏面反射（右下 = 対角）。1枚でも逆を向くと立体感が壊れる |
| 6 | **装飾を `drawingGroup()` で焼かない** | オフスクリーンに閉じるため `.screen` / `.plusLighter` が箱の中だけで完結し、ガラスと背景に対して加算されなくなる。光ではなく白い膜として乗る |
| 7 | **3つ表示に独自レイヤーを足さない** | 単体バブルが基準。差分が出るとメンテのたびに片方だけ古くなる（実際に旧 `BubbleIridescentEdge` / `GlassTubeRim` がそうなっていた） |
| 8 | **3つ表示の複数ガラスは `GlassEffectContainer` で括る** | 括らないと最前面の1つしか背後を採取せず、残りの球のガラスが消える |
| 9 | 旧OS（macOS 14/15）のフォールバック経路を必ず残す | `CLAUDEBAR_FORCE_LEGACY=1` で毎回確認する（メモリ `os-compat-check`） |

## 5. 変更の検証手順

### 5-1. ビルドとテスト（必須ゲート）

```sh
swift build && swift test        # テストは9件。緑のままであること
```

### 5-2. 見た目の 2×2 マトリクス

**外観（ライト/ダーク）× 背景（白/黒）** の4通りを必ず見る。
ガラスは素通しなので、アプリの外観と画面の内容は無関係に組み合わさる
（ライトモードでも真っ黒なエディタの上に浮くことがある）。加えて
**混色背景**（細かい市松）で「背景の模様が透けたまま明るくなっているか＝塗り潰していないか」を見る。

デバッグビルドは環境変数で外観を固定できる（`Main.swift:44-52`）:

```sh
CLAUDEBAR_APPEARANCE=dark   # または light
CLAUDEBAR_FORCE_LEGACY=1    # 旧OS経路（macOS 14/15 のフォールバック）
CLAUDEBAR_DECO=60           # 装飾の濃さ 0-100%
CLAUDEBAR_CLARITY=100       # ガラスの局所クリア化 0-100%（既定0=クリア化しない）
CLAUDEBAR_RAINBOW=100       # 虹（加算側）の濃さ 0-100%（既定90）
CLAUDEBAR_RAINBOW_SUB=0     # 虹（減算側・明るい背景用）0-100%（既定35）
CLAUDEBAR_SHADOW=0          # 落ち影の倍率 0-300%（既定100・0で無効）
```

表示個数の切替:

```sh
defaults write ClaudeBar bubbleCount 3   # 3つ表示
defaults write ClaudeBar bubbleCount 1   # 単体（確認が終わったら必ず戻す）
```

### 5-3. 撮影の手順（画面を占有しないこと）

**背景板はバブルのウィンドウ矩形だけに敷く。全画面の板は絶対に出さない**
（作業中の画面を覆ってしまう）。単体は 150×150、3つ表示は 220×210。

1. デバッグビルドを `CLAUDEBAR_DEBUG=1 CLAUDEBAR_CMDFILE=<path>` で起動する
2. コマンドファイルに1行ずつ書いて操作する（`DebugBridge.swift:1-20` に一覧）
   - `usage:32,36,44` — 使用量を偽装
   - `bubble` — バブルを表示
   - `state` — `<cmdfile>.state` に JSON を書き出す（`panel` = バブルの矩形、`screen` = 画面サイズ）
3. `state` の矩形（単体は150×150へ広げる）に単色/混色の板を `NSWindow.Level(rawValue: 2)`
   で1枚だけ出す（バブルは `.floating` = 3 なので必ず下に入る）
4. `screencapture -x -R x,top,w,h out.png`
   （AppKit は左下原点、`screencapture` は左上原点。`top = 画面高 − (y + h)`）
5. **撮影直後に板を落とす**

> ガラスは自分より広い範囲をぼかして採取するため、板が球ぴったりだと
> 板の外の実デスクトップを吸って明るく見える。板は必ず**ウィンドウ大**にすること。
> （この罠で「3つ表示だけガラスが消えている」と誤診しかけた）

### 5-4. コントラストの計測（小さい文字は 4.5:1 以上）

スクショから直接測る。円の中の「下位5%の輝度＝暗い文字」と「中央値＝地」を
WCAG 相対輝度で比べる:

```python
#!/usr/bin/env python3
# usage: contrast.py <png> <cx> <cy> <r> <画像の実寸pt幅>
import sys; from PIL import Image
def lum(px):
    f = lambda v: (v/255)/12.92 if v/255 <= 0.04045 else (((v/255)+0.055)/1.055)**2.4
    r,g,b = px; return 0.2126*f(r)+0.7152*f(g)+0.0722*f(b)
im = Image.open(sys.argv[1]).convert("RGB")
cx,cy,r = (float(v) for v in sys.argv[2:5]); k = im.size[0]/float(sys.argv[5])
cx,cy,r = cx*k, cy*k, r*k
v = sorted(lum(im.getpixel((x,y)))
           for y in range(int(cy-r), int(cy+r)) for x in range(int(cx-r), int(cx+r))
           if (x-cx)**2+(y-cy)**2 <= r*r)
n = len(v); dark = sum(v[:n//20])/(n//20); mid = v[n//2]
hi,lo = max(dark,mid), min(dark,mid)
print(f"{(hi+0.05)/(lo+0.05):.2f}:1")
```

`%` の文字帯（球の中心からやや下、半径12pt程度）で測る。合格ラインは **4.5:1**。

実測値（2026-08-27・使用率32%・ライト外観）:

| | 白背景 | 黒背景 |
| --- | --- | --- |
| 単体バブル | 11.81:1 | 7.21:1 |
| 3つ表示（セッション球） | 12.45:1 | 6.96:1 |

### 5-5. CPU

24時間常駐なので **待機中 約1%** が上限の目安。`ps` の `%CPU` は起動からの平均なので、
CPU時間の差分から実効値を出す:

```sh
read_t() { ps -o time= -p "$PID" | tr -d ' ' | awk -F: '{s=0;m=1;for(i=NF;i>0;i--){s+=$i*m;m*=60}print s}'; }
T0=$(read_t); sleep 25; T1=$(read_t)   # (T1-T0)/25*100 が実効%
```

実測（2026-08-27・3つ表示・25秒）: 改修前 **1.20%** → 改修後 **0.96%**。

## 6. 既知の行き止まり（再挑戦しないこと）

| やったこと | 結果 |
| --- | --- |
| 漂いを SwiftUI の宣言的アニメーション（`TimelineView` / `.repeatForever`）で書く | **待機中 7–13% CPU**。Apple は SwiftUI アニメにバッキング CAAnimation を持たせないため、アプリ内で毎フレーム刻む。`repeatForever` への置換も約9%で悪化 |
| 装飾を `ImageRenderer` で事前にベイクする | レイアウトが壊れた（リングが球の外に描かれた） |
| 装飾を `drawingGroup()` で焼く | `.screen` / `.plusLighter` がオフスクリーン内で閉じ、ガラス・背景への加算が効かなくなる。光ではなく白い膜になる |
| `.regular` ガラスの明暗自動フリップに期待する | 透明ウィンドウ越しには**発火しない**（実験 `flip/main.swift` で確認）。材質は `NSApp.appearance` には従うが、背後の画面の明るさには反応しない |
| `.regular` ガラスの**背後**に減光レイヤーを敷く | ガラス自身の適応輝度に打ち消される。効かない |
| `.tint()` で暗くする | 効果なし |
| ウィンドウ境界をまたぐブレンドモード | 不可能。ウィンドウの外側の画素とは合成できない |
| 画面録画権限なしで背景の色を読む | 不可能 |
| `.clear` ガラスを暗幕なしで単体使用 | 明るい背景で完全に消える（実測 1.48:1）。Apple も `.clear` は暗幕とセットで使えと指示している |
| 3つ表示で `GlassEffectContainer` を外して素の `glassEffect` を3つ置く | 背後を採取するのは最前面の1つだけ。2番目・3番目の球のガラスが消える（2026-08-27 実測） |
| `GlassEffectContainer` 配下で `.background { … glassEffect }` としてガラスを敷く | ガラスが中身より前面へ持ち上がり、文字・リングが隠れる。`content.glassEffect(...)` の形で当てること |
| 球を融合させる（メタボール／`GlassEffectContainer` の morph） | 球の位置を SwiftUI 値で動かす必要が生じ、どの実装でも 7–13% CPU。廃止済み（`MetaballShape.swift` は削除） |
| 黒い暗幕・ティント・ターミネーター・影で立体感を出す | すべて「黒いブラー」として悪目立ちした。オーナー却下 |
| 乳白ヘイズ・大きなブルームを乗せる | 透過を塗り潰して曇る。全廃 |

## 2026-08-27 追補: 局所クリア化マスクとリング前面化

レイヤー構成が上記から3点変わった（値はコードが正）:

1. **BubbleClarityMask（ガラスの局所クリア化）** — `BubbleDecoration.swift`。
   磨りのコアを重なり合う4枚のぼけた楕円（雲）で作り、境界が真円に見えないようにする。
   クリアパッチ（destinationOut）が外周寄りを素通しにする。
   単体=背景ガラス円と拡散照明に適用 / 3つ表示=`TripleBubbleGlass` がガラスごと適用し、
   文字コラムは雲が、リングは `ringFraction`（描かれている弧の真下だけの保護）が守る。
   **マスクのアルファ=ガラスの残存量**。削った場所はLiquid Glassの効果
   （ぼかし・明度適応・縁レンズ）そのものが消えて生のデスクトップになる。
   「完全に透明だがガラスっぽい」は原理的に作れない（屈折は透明ウィンドウ越しに効かない）
2. **リングは虹より前面** — 単体は装飾ZStackの最上段、3つ表示はガラス部分木内の最上段。
   3つ表示でリングを兄弟レイヤーへ出すのは不可: GlassEffectContainer がガラスを
   兄弟より前面へ集約するため、磨りガラス越しのボケた塊になる（実測）。
   同様に光沢/虹を兄弟に出すと加算が透明背景に対して効いてフル彩度で暴走する（実測）
3. **薄膜バンドを内側へ拡大**（filmBandStops）+ 文字コラムの白パッド（拡散照明に追加）

**新ハマりどころ**: 静的な形のマスクでもライブのblurツリーのまま使ってはいけない。
ガラスは漂いで背景が毎フレーム変わり再描画されるため、マスクの7枚のぼかし楕円が
毎フレーム再合成され、単体バブルのGPUが0.17→0.62GPUコア相当/秒（3.5倍）に跳ねた。
`drawingGroup()` で1枚のテクスチャに焼くと0.20まで回復。
（※装飾の加算レイヤーへの drawingGroup 禁止則とは別物 — マスクはアルファしか使わないので焼いてよい）

**検証用の暫定フラグ**: `CLAUDEBAR_EDGE=hairline|limb` — 白背景で
バブルが消える問題への減光系候補（既存装飾は全加算なので白の上では原理的に不可視）。

## 2026-08-27 夜 追補: 局所クリア化は既定オフ（Liquid Glassを全面に戻した）

上の「局所クリア化」は**既定で無効**になった（`BubbleClarity`・既定0）。
クリア化はガラスを削る操作で、削った場所は Liquid Glass の効果ごと消える。
ユーザー判断は「**ガラスの質感の方を取る**」（拡大前＝テスト版9.9.9の見た目が好み）。

| ノブ | 実体 | 既定 | 備考 |
| --- | --- | --- | --- |
| `BubbleClarity` | `CLAUDEBAR_CLARITY` 0-100 | **0** | 0でマスクごと外す（ぼかし楕円7枚＋`drawingGroup`の合成コストも消える） |
| `BubbleRainbowStrength` | `CLAUDEBAR_RAINBOW` 0-100 | **90** | `filmBandStops` の peak に掛かる（加算側 `.screen`） |
| `BubbleRainbowSubtractive` | `CLAUDEBAR_RAINBOW_SUB` 0-100 | **35** | 同じ帯を `.multiply` で重ねる層。**白背景で虹を出す唯一の手** |
| `BubbleShadowStrength` | `CLAUDEBAR_SHADOW` 0-300（倍率%） | **100** | 落ち影を**本実装**。ライト/ダーク両方で出す（外観で分岐しない） |

- **白い背景では加算（`.screen`）の虹は原理的に見えない**（screen(白, 色) = 白）。実物の薄膜は
  反射（加算）と同時に透過光から補色を抜くので、同じ帯を `.multiply` でも重ねて解決した
  （`BubbleRainbowSubtractive`）。暗い背景では「暗い値 × 色 ≒ 暗い値」でほぼ無効になるため、
  従来の見た目は壊れない。強さは 0/35/55/80 で撮り比べて35を採用（55は出過ぎ）
- `filmBandStops` は拡大前の分布へ戻した（0.55/0.74/0.86/0.94）。「もう少し虹を」の
  依頼が来ても、まず `CLAUDEBAR_RAINBOW` で当たりを付けてから停止位置を触ること
- 文字コラムの白パッド（拡散照明の楕円）は**クリア化の補償**なので、クリア化オフでは描かない。
  ガラスが全面にあるときに足すと白く曇るだけ
- 落ち影は加算装飾では作れない唯一の「暗くする」要素。白背景で球が消えないための実装で、
  暗い背景では自然に沈む。マスクで本体シルエットをくり抜いているので球の中は暗くならない
- 落ち影は**2層**（環境光: 黒0.09・blur 22s・y+2s / キーライト: 黒0.21・blur 11s・x+1.5s y+5s）。
  1層だけだと「濃くすると汚い・薄くすると見えない」の両立ができない。光源は左上（グロスの位置）
  なので影は右下へ流す。**「重い」と言われたら濃さより先にぼかし半径を広げる** — 同じ暗さの
  総量でも、広い影は軽く見える（`CLAUDEBAR_SHADOW_BLUR` で倍率比較して 2.5倍を採用）

## 2026-08-27 夜 追補2: 3つ表示の「独立漂い」が効かない理由（macOS 26のみ）

**症状**: 3つ表示で球ごとの漂い（`DriftHost`）が画面に出ず、3球が1つの塊として動く。

**切り分け（すべて実測）**:

| 確認したこと | 結果 |
| --- | --- |
| `DriftHost` のCAAnimationは張られているか | 張られている（`CLAUDEBAR_TRACE_ANIM=1` で `drift-x/drift-y`） |
| presentationレイヤーは動いているか | 動いている（球ごとに違う値・±9pt） |
| 画面上の見た目は動くか | **動かない**（窓ローカルのキャプチャを位相相関で計測。3球とも同一変位） |
| `position` の代わりに `transform.translation` | 同じく効かない |
| `CLAUDEBAR_FORCE_LEGACY=1`（Material経路） | **効く**（3球バラバラに動く） |
| 塊側（`startFloating`＝アセンブリのレイヤー）の漂い | 効く |

**原因**: `glassEffect` の描画は**最も外側のNSHostingViewを基準にウィンドウ単位のガラス群へ持ち上げられ**、
その内側のレイヤーアニメーションを無視する。ガラスを content に掛けている3つ表示では
球まるごと（リング・文字・装飾とも）が持ち上げ対象になるため、球単位では一切動かない。
※ 外側のSwiftUIツリーに置いた `GlassEffectContainer` が、`DriftHost` の内側（別ホスティング
ビュー）のガラスに効いていたのも同じ理屈。単体バブルはガラスを `.background` に敷き、
`WobbleHost` はガラスの外側にいるので中身のゆらぎは効く。

**検証済みの回避策**: 球ごとに**独立したNSHostingViewをアセンブリ直下の兄弟として**置き、
各ホストのレイヤーにCAAnimationを張る。単体実験（`scratchpad/glasstest.swift`）で
①3球が独立に漂う ②3球とも背後を採取する（＝ガラスが効く）ことを確認した。
つまり「持ち上げ先」が球ごとに分かれれば解決する。

**採らない案**: SwiftUIの `.offset` で動かす（ガラスはレイアウト位置には追従する）。
これは2026-08-21に実測済みで、実装方式によらず待機中CPU 7-13%（現在は約1%）。
